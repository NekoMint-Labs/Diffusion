# 第二轮浏览器真实模型对比

日期：2026-10-29（Asia/Shanghai）。工程与功能测试、模型输出质量、Windows 原生验收分别记录。

## 结论

**本轮不支持宣称候选版稳定改善模型体验，也不建议据此默认采用整组功能。** 同一公开输入、DeepSeek deepseek-v4-pro、Standard、max_tokens=1600 下，基线六组中五组有卡片，候选六组中三组有卡片。四条无卡片响应均为服务 200、finish_reason=length、1600 completion token 全部记作 reasoning token、正文为空。

这是十二次固定配置的单次观察，不能推断稳定成功率，也不能把差异单独归因于观点提示。它直接说明该配置存在“服务响应成功但用户拿不到正文”的交付问题。下一步优先验证推理模型的预算/结束原因适配，再比较提示内容，不宜继续仅做展示优化或通过截断/自动重试补表面成功。

八条有效输出经真实浏览器 Read → Keep → 下载导出 → 界面恢复至新项目，正文与卡片均逐字一致。所有有效正文为 40–79 个 Unicode 字符，均不超过 120，因此直接显示全文是正确短文路径；本轮**没有覆盖长文观点持久化或观点与全文的忠实程度**。

## 固定版本与方法

- 基线：#81 79a484483e882c0b252b46c09391f7a3cd84f027，readingTrial=1，独立 4192 origin。
- 候选：#83 + #88 的 5e4f979c5c210246577280ac91fd58d2631d8920，readingTrial=1&propositionTrial=1，独立 4191 origin。
- 两个生产 bundle 在用户配置 key 之前封存；采集前逐一重算实际服务资产哈希并核对页面已加载的脚本。两者沿同一独立 Chromium profile 的不同 origin 运行，未访问日常 4175 Field。
- 用户在两个既有设置页分别配置会话 key。工具只核对保存状态与非秘密模型配置，不读取 key/认证头、不进行连接测试或模型 warmup。所有十二条实际模型均由服务报告为 deepseek-v4-pro，输出预算均 1600。
- 同一公开合成六情境；每对完整 fixture SHA-256 相等。每条一次 POST；Angle/Diffuse UI 配置一步，实际各一次请求。无搜索、无手动提炼、无自动重试；两个版本顺序执行。

## 逐组结果

| 情境 | 基线 | 候选 | 质量判读 |
| --- | --- | --- | --- |
| Ask | 截断，无正文/卡片 | 截断，无正文/卡片 | 两边均未交付答案，不能判断直答是否改善 |
| Continue | 有卡片，区分自述需要与可观察使用行为 | 截断，无正文/卡片 | 基线有可继续发展的新划分；候选未交付 |
| Another Angle | 有卡片，以失败信号换视角 | 截断，无正文/卡片 | 基线改变视角，但“两周收不到信号可能需求弱”缺少招募/观察条件，不应当作已验证判断 |
| Diffuse | 追问需要的可观察定义 | 给出主动询问/愿意再用的观察例子 | 候选更具体；与基线属于相近验证方向，单样本不足以说整体更独特 |
| 前提纠正 | 考前复习、自评薄弱点，保留未验证限定 | 考前复习及隐私约束仍在 | 两边未沿用作业辅助目标；候选“内容只能来自考纲或当场提问”把隐私边界扩成排他来源，原输入没有支持这个“只能” |
| 不确定性 | 自述不能证明需求成立 | 自评不能证明问题存在 | 两边保留不确定性，候选仍是较泛化的自评提问；未证明改进 |

判断依据见[逐字对照](逐字对照.md)，不以“是否逐字提到两小时”作为单一通过标准。关注回答是否推进问题、是否尊重仍适用的边界、是否额外编造要求。

## 生成之外的核对

八条有效卡片的完整原文、画布文字、Read 文本、Keep 后文字、导出及新恢复项目正文全部一致。八条都走短正文直显，没有自动提炼、后台补写或额外请求。失败条保留可见的 incomplete-answer 提示，没有生成虚假的成功卡片。

基线采集到前三条后，在切换至 Diffuse 情境时，工具将尚未加载的列表误当成当前 Field，停在切换等待。该次记录为零请求，见 [原始工具失败](baseline-diffuse-setup-failure.json)。修复为等待目标列表项可见再判断；新增模拟异步挂载的生产浏览器回归通过。随后只在新目录继续原本尚未请求的 Diffuse、correction、uncertainty 三组；没有重跑 Ask/Continue/Angle，没有替换旧失败。本轮候选所有六组使用修复后的相同工具步骤；产品源码、bundle、输入、模型/预算未改。

## 数据与限制

- 正式主生成 12 次；8 次交付卡片，4 次截断。工具设置失败 1 次，主生成 0 次，单独保留。
- 服务报告合计 prompt token 23584、completion token 14749，其中 reasoning token 14315；缓存明细保留在每条 usage。未换算价格，不等于独立核对的账单，也不比较延迟。
- [配对清单及哈希](comparison-manifest.json)列出全部十二条记录；完整模型 content 与 usage 在原始 JSON，未发布 profile、API key、认证头或私人 Field。截图保留本机，不随本报告上传。
- 新旧版本有多处差异，随机模型每组仅一次。不能据 5/6 对 3/6 声称总体回归率，也不能声称观点提示是唯一原因。
- 本环境没有原生实例/Rust 构建工具；这些是浏览器路径，不能代替 Windows 原生复测、物理输入法/触摸板或系统重启验收。#85 的既有原生材料仍独立保留。

## 建议下一步

先做一个有上限的推理模型交付实验：明确区分内部推理预算和可见正文交付，保存 finish_reason/usage/空正文，比较预算调整或模型实际支持的推理开关，禁止静默自动重试。未经实际支持核实不随便发送供应商参数，也不把上限无限增大。

其次处理无依据的“只能/必须”限制：沿来源与用户授权边界生成建议，允许给出选择，但不得把“不要接触私人作业/成绩”解释为“只能用两类来源”。这需要真实输出复核，不宜仅靠关键词删除。

待可见答案稳定交付后，再用含长正文的明确任务核对观点/全文关系及同候选 Windows 体验。本轮没有新增预算实验或修改生产提示/请求预算，没有合并或发布。
