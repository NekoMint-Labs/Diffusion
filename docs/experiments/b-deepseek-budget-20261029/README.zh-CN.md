# DeepSeek V4：固定八次预算对比

日期：2026-10-29（Asia/Shanghai）。本报告接续 #89；上一轮十二次调用和原始报告不改写。

## 结论

**本轮完成了八次真实调用，七次返回卡片；可以保留预算适配为候选，但还不能选定产品默认参数。**

| 参数 | Ask（直接问） | Continue（继续想） | completion token（Ask / Continue） |
| --- | --- | --- | --- |
| 推理 high，上限 1600 | 无正文，length | 有正文 | 1600 / 870 |
| 推理 high，上限 4000 | 有正文 | 有正文 | 1258 / 938 |
| 推理 low，上限 1600 | 有正文 | 有正文 | 801 / 1304 |
| 关闭推理，上限 1600 | 有正文 | 有正文 | 123 / 73 |

Ask/high/1600 再次出现 HTTP 200，但 1600 completion token 全部记作 reasoning，content 为空。其余七条均为 HTTP 200、finish_reason=stop、服务报告模型 deepseek-v4-pro。

**不能把这张表解释为“4000 已解决问题”或“关闭推理最优”。** 每格只有一次；两个 high/4000 实际 completion 都不足 1600，high/1600 的 Continue 也成功，说明存在单次输出差异。关闭推理的 Ask 虽然有具体操作，却给出缺乏依据的停止规则，见下文。参数改变、次序、缓存和随机输出都不能在这两个场景中被充分分离。

## 固定版本与执行边界

- 产品 bundle：#83 + #88，5e4f979c5c210246577280ac91fd58d2631d8920；readingTrial=1&propositionTrial=1。每次运行前核对服务资产 SHA 与页面实际加载脚本。
- 工具首次 d7808d5，续跑 a6f36f1；修改仅在 Playwright 实验路由中作用于三个请求参数。产品源码、提示、默认模型设置均未改。
- 两个合成公开场景，Ask 按表格顺序，Continue 反向。每次从本工具专用 fixture 重置；同一场景的完整请求规范化哈希一致，只忽略 requestId 与三个实验参数。服务返回 prompt token 可因推理配置/缓存而不同，不据此声称请求文本改变。
- 共 8 次、累计 max_tokens cap 17600；实际服务报告 prompt 15522、completion 6967，其中已报告 reasoning 6384。关闭推理两次未提供 reasoning 字段，不能把缺失字段当作独立实测的数值。未核算费用或账单，也不比较速度。
- 无自动重试、额外提炼、搜索、连接测试或 warmup；保持产品 45 秒超时。密钥由用户在专用设置页填写，只核对保存标记；未读取/复制 key 或认证头，未访问日常 4175 数据。
- control 显式传 enabled/high，对应官方当前默认行为；它不是上一轮请求的逐字重放。

官方依据（本日核对）：[推理模式](https://api-docs.deepseek.com/guides/thinking_mode/)与[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。推理默认 enabled/high；V4 支持 low/high/max 及关闭推理；max_tokens 包含内部推理和可见输出。此结论不能推广给未知模型。

## 输出质量：能返回不等于能帮助用户

完整原文与画布文字见[逐字输出](逐字输出.md)。以下是人工判读，不是自动指标或用户验收：

- Ask/high/4000 提出了访谈和一个可直接问的问题，但“每周问 5–10 人”未经可行性验证，只能当建议，不能当成功门槛。
- Ask/low/1600 提出了短访谈，标出能联系到学生的假设；但“确认痛点是否存在”说得过满，访谈只能提供线索。
- Ask/off/1600 给出论坛、公开评价、应用差评等例子，比抽象表述具体；但“两小时没看到就停止、不接触学生”把有限的观察变成排他规则，没有足够依据。不因生成成功就接受它。
- Continue/off/1600 建议观察是否主动使用整理模板，可作为小试用；“复习缺乏外部触发”等语言仍需改得通俗。
- Continue/low/1600 建议问卷及主题收集，但表达仍绕；还应区分“说想要”与“实际愿意使用”。
- Continue/high/4000 与 high/1600 都保留“这只是线索/假设、不是需求已验证”的边界；需要进一步给出具体看什么、如何记，才能更好地帮助使用者。

#89 于本日收到 A 方向使用者反馈：回答抽象、难理解，尚不能比较两种方案的帮助。该反馈与本轮判读一致，但不是对本轮新八条输出的用户验收。**下一轮优先研究日常语言、一个具体动作和例子，以及不把建议写成用户限制。** 不再单凭 JSON 合法、有卡片或提到时间就算质量通过。

## 阅读与持久化核对

七条有效正文均完成 Read → Keep → 下载导出 → 从界面恢复至新项目，原文逐字相等，Keep 与恢复后的卡片文字相等。正文长度为 66、71、179、92、93、93、129 个 Unicode 字符。

其中 179 和 129 字两条走首段预览，原文入口可用，导出/恢复保存全文；其余五条直接显示短正文。模型只在一个短正文响应中返回 reading.point，没有得到长正文的模型观点。因此本轮补到了长正文的预览与全文保存路径，**仍没有证明长正文“提炼观点”的忠实程度或体验提升**。

## 工具中断与续跑

首次 Ask/high/1600 已完整保存。下一配置在切换至 hold Field 时，五秒的 storage 轮询超时，真实请求为零，见[原始失败](zero-request-switch-failure.json)。稍后只读检查已处于 hold，无保存错误；两次无模型切换约 746/727ms，未复现原延迟，不声称定位了产品缺陷。

工具改为先等待 Open Field 窗口关闭，再核对项目 ID 与标题。新增 --resume：核对旧计划、构建、提示、逐次记录与预算，已发出的调用不得再跑；从新目录只运行余下七臂、cap 16000。旧文件原样保留，[续跑凭据](resume.json)记录原文件 SHA；[清单](comparison-manifest.json)记录已归档原始文件 SHA。原始失败没有计为模型失败，也没有被新的成功覆盖。

续跑工具编辑期间有一次语法错误，在启动模拟浏览器前就退出，真实请求为零，修正后才继续验证与正式执行。
