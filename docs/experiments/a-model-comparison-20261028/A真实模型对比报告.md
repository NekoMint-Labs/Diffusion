## 最值得处理的三个问题

### 1. Keep 之后的观点连续性尚不完整

复现脚本实际运行了 Controller 的 Keep 和真实 ThoughtView 的服务端渲染：

```json
{"beforeKeepShowsPoint":true,"afterKeepShowsPoint":false,"originalPreserved":true,"propositionPreserved":true,"keptGenerationAction":null}
```

这是合成的长文 Diffuse 样例，证明已知显示资格断点；不是本轮真实 Diffuse 长文复现或已修复的证据。本轮真实 Diffuse 尚未完成可见卡片采集。

建议：明确生成内容在 Keep 前后的展示资格；同 ID 的正文和匹配观点应一起保持；缺少观点时仍可显式提炼。不要为通过判断而把 Diffuse 冒充 Continue。修复后补浏览器 Keep→重启→阅读全文回归，再做独立 Windows 试用。

### 2. “可执行建议”必须满足真实时间限制

候选 Ask 原文建议“3–5 次 20–30 分钟”的访谈。范围上限为 150 分钟，超过每周两小时；它又说第一周先问 3 人，造成计划范围含混。卡片没有显示两小时限制。

建议：A 的评阅标准应包含最坏情况下的总耗时，明确“本周最多做多少”；如果时间限制改变建议成立的条件，观点也应保留。不能只检查语气和格式。

基线也有推理风险：纠正场景的“若没有学生主动提供的题目，系统就无法判断复习需求是否真实”把某一种证据路线说成必要条件，缺乏依据。这条建议不应因为保留了新前提就被判为通过。

### 3. 默认预算与失败体验会直接影响产品价值

候选纠正样例返回 `finish_reason: length`，服务记录显示 completion 为 1600 token，其中 reasoning token 也是 1600，正文为空。两版 Another Angle 都超时。

这支持“当前这组服务/深度配置存在实际交付风险”，不支持“所有模型都不行”。建议 B 先校准此模型的正文预算、超时和停止反馈；A 复测时必须继续记录空结果和失败，不能只展示最好的一张卡。

## 采用建议与协作分工

- **保留方向**：可选观点必须绑定完整原文；短答案直接显示原文；缺失观点时诚实标注预览；Keep 不代表事实认证。
- **暂缓默认采用**：本轮没有证明所有长回答都能产生忠实、独立、可持续保存的观点。
- **A 下一轮**：用同样话题评阅时间、隐私和不确定性；另外找非设计参与者完成短时探索与隔天续接，不把我的评阅当真人偏好。
- **B 优先项**：修复 Diffuse Keep 展示资格并补回归；处理实际模型的预算/超时；确认手动提炼不会悄悄变成额外请求。
- **C 优先项**：验收远景/近景下建议的可发现性、阅读入口和 Keep 后连续性；普通 Diffuse 本轮没采到卡片，需要独立交互复核，不能仅凭渲染器可运行就宣布可用。

## 验证与限制

- 目标单元测试：4 文件、42 项通过，见 `targeted-unit-tests.txt`。它们证明工程规则，不证明模型质量。
- 两版原生 release 编译成功；可执行文件摘要见 `native-build-hashes.json`。这是隔离原生测试，未制作或安装新发布包，没有升级正在使用的软件。
- 原计划六组配对、12 次生成。正式入表实际为 **14 次原生生成请求**：普通 Diffuse 的 UI 入口默认三步，首个服务候选返回后尝试停止，两版都已启动第二个请求。故 Diffuse 不满足原方案“单步单次”条件，完整验收仍欠缺。
- 普通 Diffuse 的两次入表运行均有服务正文，但没有被脚本采集到可见卡片。记录中的 `empty-or-failed` 是脚本分类，不可解释成模型确实为空；报告已经作此更正。
- 更早的 v1 试跑错误地尝试替换只读桥接函数，导致请求观测失败；其中 `requests: []` 不能解释为未调用或未计费。故障记录原样保留在 `live-v1-instrumentation-failure/`，未混入正式配对。
- v2 的纠正夹具缺少内容合同要求的 `generationAction`，被启动校验拒绝，没有生成请求。v3 修正为与生产 authored-response 结构一致，并在写入前调用正式校验器；这是合成的历史链，不是真实用户回应过程。
- 候选 Ask/Continue/Angle 取自 v2，其余候选和全部基线取自 v3；每组精确路径列在 manifest，不挑选同条件下多次生成的最好结果。
- 有部分隔离运行在墙钟时间上重叠，且供应商可能使用缓存；本报告不比较响应速度或费用。没有稳定性统计、物理输入法/触控板验收、搜索验收或完整长期研究验收。

本轮没有改动生产行为或向 GitHub 发消息。可以据此提出修复和下一轮验收条件，不能据此声称团队已批准 #83。
